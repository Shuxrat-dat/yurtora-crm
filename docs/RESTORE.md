# Резервные копии и аварийное восстановление Yurtora CRM

Рассчитано на один сервер с `docker-compose.prod.yml`. Проверено вживую (14.10.2026): копия базы, проверка целостности, восстановление во временную базу и сверка данных.

## Цели

| Показатель | Значение | Как обеспечивается |
|---|---|---|
| RPO (сколько данных можно потерять) | до 24 часов | сервис `backup` делает дамп раз в 24 ч; для RPO ≈ 1 ч уменьшите `INTERVAL_HOURS` (база ~150 МБ за 3 года, дамп занимает секунды) |
| RTO (за какое время поднять систему) | 2–4 часа | новый сервер + `docker compose up` + восстановление дампа по инструкции ниже |
| Хранение | 14 дней на сервере + копия вне сервера | `BACKUP_KEEP_DAYS`, `BACKUP_COPY_DIR` |

## Как это работает

1. Сервис `backup` каждые 24 часа делает `pg_dump` в `./backups/yurtora_crm_ГГГГММДД_ЧЧММСС.sql.gz`.
2. Каждая копия проверяется (`gzip -t`, минимальный размер). Результат пишется в файлы:
   - `backups/LAST_OK` — время последней успешной копии;
   - `backups/LAST_FAILED` — время последней неудачи (пропадает после следующей успешной).
3. Healthcheck сервиса `backup`: если успешной копии не было 36 часов, контейнер становится **unhealthy**. Проверка: `docker ps` (колонка STATUS) или `docker compose -f docker-compose.prod.yml ps`.
4. **Копия вне сервера — обязательна.** Диск сервера может выйти из строя вместе с копиями. Настройте один из вариантов в `.env`:
   - `BACKUP_COPY_DIR=/offsite` и `BACKUP_COPY_HOST_DIR=/путь/к/второму/диску/или/NAS` — копия кладётся ещё и туда;
   - `BACKUP_UPLOAD_CMD='rclone copyto "$BACKUP_FILE" remote:yurtora/'` — любая команда загрузки (нужен образ с этой утилитой).

## Проверка восстановления (раз в неделю и перед запуском)

Не трогает рабочую базу: восстанавливает последнюю копию во временную базу `restore_check_*`, сравнивает число учеников, групп, записей, пользователей, проводок и сумму книги проводок, затем удаляет временную базу.

```bash
docker compose -f docker-compose.prod.yml run --rm --entrypoint sh backup /scripts/restore_check.sh
```

Ожидаемый вывод заканчивается строкой `MUVAFFAQIYATLI: zaxira tiklandi va asosiy baza bilan mos`. Если появилась строка `FARQ`, это может быть следствием новых записей после копии; если расхождение большое, копия не годится.

## Аварийное восстановление на новом сервере

1. Установите Docker, склонируйте репозиторий (`git clone`), создайте `.env` по образцу `.env.example` (те же `SECRET_KEY`, `POSTGRES_PASSWORD`, токен бота; `DOMAIN` — новый домен).
2. Скопируйте последнюю копию из внешнего хранилища в `./backups/`.
3. Запустите только базу:
   ```bash
   docker compose -f docker-compose.prod.yml up -d db
   ```
4. Восстановите данные (копия содержит `DROP ... IF EXISTS`, поэтому подходит и для пустой базы):
   ```bash
   gunzip -c backups/yurtora_crm_ГГГГММДД_ЧЧММСС.sql.gz | \
     docker compose -f docker-compose.prod.yml exec -T db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v ON_ERROR_STOP=1'
   ```
5. Поднимите остальное: `docker compose -f docker-compose.prod.yml up -d --build`. Миграции применятся автоматически.
6. Проверьте: вход директором, число учеников, баланс одного ученика, последний платёж.
7. Запишите время и результат (для следующих проверок).

## Что не защищено этой схемой

- Данные между двумя копиями (до 24 часов). Для критичных дней сделайте ручную копию: `docker compose -f docker-compose.prod.yml run --rm -e RUN_ONCE=1 --entrypoint sh backup /scripts/backup.sh`.
- Копии не зашифрованы. Храните внешнюю копию в доступе только для владельца; при необходимости шифруйте в `BACKUP_UPLOAD_CMD` (например, `age` или `gpg`).
- Файлы сертификатов Caddy лежат в томе `caddy_data`: при потере они выпустятся заново автоматически.

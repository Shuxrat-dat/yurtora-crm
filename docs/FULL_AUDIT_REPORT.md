## 4. Проверка базы данных

### 4.1 Схема (по фактическим моделям)
Присутствуют: ученики, родители (`Guardian` + связь), преподаватели, курсы, группы, записи в группы + журнал записей, кабинеты, слоты, уроки, посещаемость + журнал, книга проводок, зарплатные ведомости/строки/корректировки/выплаты, категории и статьи расходов, журнал действий, Telegram-контакты/токены/журнал отправок/сводки.

**Деньги:** везде `BigIntegerField` в сумах (PASS, float нет). **Первичные/внешние ключи:** FK везде заданы; правила удаления разумные (`PROTECT` для финансов, групп, уроков, `CASCADE` для посещаемости и контактов, `SET_NULL` для авторов). **Уникальность:** `unique_charge_per_enrollment_lesson`, `unique_excused_credit_per_charge`, `unique_open_enrollment_per_group`, `unique_lesson_student_attendance`, `unique_group_date_start_time`, `unique_payroll_year_month`.

**Отсутствуют (подтверждено выводом `Meta.constraints`):**
- **CHECK-ограничений нет ни одного** (DB-01): знак суммы по типу проводки (`charge < 0`, `payment > 0`), `teacher_percent` 0–100, `capacity > 0`, `end_time > start_time`, `max_students > 0` защищены только валидаторами форм и сервисов, но не БД.
- Телефон ученика не уникален, дубликаты не ищутся при создании вручную (DB-02); импорт Excel дедуплицирует по `телефон+имя+фамилия`.
- Неизменяемость `LedgerEntry` обеспечена только в Python; прямой SQL `UPDATE` выполняется успешно [ИЗМЕРЕНО] (DB-03).

**Индексы:** есть на `Student(phone, last_name, status)`, `Lesson(date; group,date)`, `Attendance(lesson; student)`, `LedgerEntry(student,group; group,entry_date; kind)`, `AuditLog(model,object_id)`, журнал отправок. Индексы FK Django создаёт сам. Поиск по имени (`icontains`) не индексируется: при 500 учениках это незаметно (24–36 мс), при нескольких тысячах потребуется `pg_trgm` (INFO).

**Миграции:** `makemigrations --check` — «изменений нет» (PASS); все миграции применяются с нуля на PostgreSQL (тесты создают БД заново, PASS).

## 5. Оценка нагрузки на 500 учеников

**Метод:** одноразовый скрипт во временной БД `test_yurtora_crm` на том же PostgreSQL (создана и удалена скриптом, рабочая БД не затронута), **синтетические** данные, без реальных персональных данных. Сервер приложения — тот же Django, запросы через тестовый клиент в процессе (без сети, TLS, nginx и gunicorn).

### 5.1 Объём данных [ИЗМЕРЕНО]
| | 1 год истории | 3 года истории |
|---|---|---|
| Ученики / записи в группы | 500 / 600 | 500 / 600 |
| Уроки | 5 085 | 14 460 |
| Посещаемость | 93 900 | 281 400 |
| Книга проводок | 101 713 | 303 159 |
| Журнал действий | 15 800 | 45 016 |
| Размер БД | 56 МБ | **143 МБ** |

Крупнейшая таблица — книга проводок (76 МБ за 3 года), затем посещаемость (44 МБ). Предположение [ОЦЕНКА]: примерно 100 МБ в год, к 5 годам около 250–300 МБ. Для PostgreSQL это очень малый объём.

### 5.2 Сценарии
**A — 500 учеников, обычная работа (1 пользователь).** Все 20 проверенных страниц отвечают за 7–765 мс; кроме финансовой панели все быстрее 330 мс. **Вывод: нагрузки нет.**

**B — активная работа (10 параллельных потоков, 150 запросов).** 19 запросов/с, медиана 146–402 мс, p95 1,1–1,5 с, максимум 1,8–3,4 с [ИЗМЕРЕНО]. Ограничения замера: потоки делят один процесс Python (GIL), поэтому CPU-нагрузка завышена; счётчик «ошибок» включает ожидаемые ответы 403 (администратор открывал страницы, закрытые для его роли), поэтому ошибки 5xx отдельно не разделялись. Предположение [ОЦЕНКА]: 3 воркера gunicorn и реальные 5–10 одновременных сотрудников для одного филиала не создают проблем; узкие места только финансовая панель и выгрузки.

**C — 500 учеников и 3 года истории.** Деградация заметна только там, где есть расчёт балансов по всей книге проводок: список учеников с фильтром «Qarzdorlar» 107 → **582 мс**, список 83 → 372 мс, выгрузка должников 324 → 811 мс. Планы запросов [ИЗМЕРЕНО]: агрегат должников 45 мс (HashAggregate по 303 тыс. строк), баланс одного ученика 1,1 мс, доход за месяц 1,6 мс, касса за день 1,5 мс, журнал действий 0,5 мс. В последних 6 страницах прогона C счётчик запросов показал 0 из-за закрытия соединений потоками (артефакт замера), времена при этом корректны.

### 5.3 Что не измерялось (NOT TESTED)
Загрузка CPU/RAM/диска хоста, число соединений PostgreSQL под реальным gunicorn, TLS, сеть, работа по медленному каналу, одновременная запись платежей разными сотрудниками, nginx/прокси. Для подтверждения нужен прогон на целевом сервере с gunicorn (3 воркера) и инструментом нагрузки (например `locust`), метриками `pg_stat_statements` и `docker stats`.

### 5.4 Вывод
Выдержит ли система 500 учеников: **да, по измерениям на синтетической нагрузке**. Запас большой для чтения; ограничением станут N+1 на финансовых страницах при росте числа учеников (655 запросов при 500 учениках, [ОЦЕНКА] около 1300 при 1000). Исправление N+1 — условие P1, не блокер.

## 6. Аудит безопасности

### Подтверждено проверкой (PASS)
- **IDOR/BOLA:** преподаватель получает 403 на карточку чужого ученика, чужую группу, чужой урок, финансовую панель, чек, выгрузку учеников; администратор — 403 на журнал действий и финансовую панель; аноним — 302 на вход [ИЗМЕРЕНО в тестовом прогоне].
- **Ограничение перебора пароля:** django-axes, 5 попыток на пару логин+IP, блок 30 минут (тесты проходят; блокировка реально сработала у вас в работе).
- **Пароли:** хешер Django по умолчанию (PBKDF2), 4 стандартных валидатора.
- **SQL-инъекции:** сырой SQL только в `seed_demo` (с защитой по имени БД); фильтры через ORM.
- **XSS:** `|safe` стоит только на JSON, собранном `json.dumps` из чисел и меток (`finance/dashboard.html`); автоэкранирование включено.
- **CSRF:** `CsrfViewMiddleware` включён, формы с токеном; `@csrf_exempt` в проекте нет.
- **CORS:** не настроен и не нужен (нет API). **SSRF/path traversal/десериализация:** соответствующих функций нет.
- **Токен бота и пароли** в логи не попадают: сообщение об ошибке Telegram не содержит URL с токеном (тест есть).
- **Секреты в git:** `.env`, базы и архивы не отслеживаются. Токен Telegram в истории не найден.
- **Production-настройки:** `check --deploy` на prod-окружении даёт одно необязательное предупреждение (HSTS preload).
- **Контейнеры `web` и `bot`** работают не от root (uid 1000).

### Найденные проблемы
См. таблицу в разделе 13: SEC-01…SEC-11. Главные:

- **SEC-01 (MEDIUM). Формульная инъекция в Excel/CSV.** `openpyxl` записывает строку, начинающуюся с `=`, как формулу (проверено: `data_type = f`). Имена учеников и комментарии попадают в `export_students_xlsx` и CSV должников. Нужна нейтрализация (`'` перед `=+-@`).
- **SEC-02 (MEDIUM). Админ-сайт Django `/admin/`** доступен любому `is_staff` и позволяет править `Attendance`, `Lesson`, `Enrollment`, `Group`, `User` напрямую, минуя сервисы начислений и проверки ролей. Финансовая книга в админке только для чтения (PASS).
- **SEC-04 (MEDIUM). За обратным прокси** `axes` и журнал действий возьмут IP прокси (`REMOTE_ADDR`): блокировка превращается в «пара логин + IP прокси», любой может заблокировать вход директору, а IP в журнале бесполезен. Нужна настройка доверенного прокси.
- **SEC-05 (MEDIUM). Нет смены и восстановления пароля и нет интерфейса управления пользователями**: пользователи и роли создаются только через `/admin/` или `create_user.py`.
- **SEC-03 (LOW). Открытый редирект** в 6 местах (`next` проверяется `startswith("/")`, что пропускает `//evil.example`): `finance/views.py:72,100`, `groups/views.py:211,234,269,292` [ИЗМЕРЕНО: `Location: //evil.example/phish`]. Эксплуатация требует POST с CSRF-токеном, поэтому серьёзность низкая; исправляется `url_has_allowed_host_and_scheme` (он уже применён в двух других местах).
- **SEC-07 (MEDIUM). Ротация секретов:** в первом коммите истории были старые dev-значения `SECRET_KEY` и пароля БД, те же значения использует ваш локальный `.env`. Репозиторий приватный; перед боевым запуском значения необходимо **заменить** (ротация нужна).
- Прочее LOW: сессия 2 недели без таймаута простоя (SEC-08), нет CSP (SEC-09), текст напоминаний с суммами долга хранится в журнале отправок (SEC-10), распаковка xlsx не ограничена по размеру (SEC-11).

## 7. Финансовый модуль

**Сильные стороны (проверено):**
- Книга проводок неизменяема в Python: `save()` существующей записи, `queryset.update()` и удаление выбрасывают исключение [ИЗМЕРЕНО]; администрирование только для чтения.
- Начисление за урок идемпотентно: `unique_charge_per_enrollment_lesson`; три теста параллельных начислений выполнены на PostgreSQL и прошли.
- Баланс считается из записей, не хранится; деньги целые.
- Запрет платежей в закрытом месяце зарплат, роль `director` для корректировок.
- Исправление ошибки делается встречной записью (поле `reverses`, корректировки).

**Проблемы:**
- **FIN-01 (HIGH). Нет защиты от двойного платежа.** Две одинаковые отправки формы подряд создали две проводки [ИЗМЕРЕНО]. Запись нельзя удалить, исправляется только корректировкой. Причины: нет идемпотентного ключа, кнопка отправки не блокируется, нет проверки «такой же платёж за последние секунды». Файлы: `apps/finance/views.py` (`PaymentCreateView`, `PaymentModalCreateView`, `QuickPaymentView`), `apps/finance/services.py:register_payment`.
- **DB-03 (LOW).** Неизменяемость не защищена на уровне БД: привилегированный доступ к PostgreSQL может изменить записи без следа. Рекомендуется триггер `BEFORE UPDATE OR DELETE` на `finance_ledgerentry`.
- **DB-01 (MEDIUM).** Нет CHECK-ограничения на знак суммы по типу проводки.
- **Журнал изменений:** кто и когда создал платёж, видно по `created_by` и `created_at` проводки; журнал действий `/audit/` фиксирует изменения справочников, но не платежи (платежи фиксирует сама проводка). Удобного экрана «кто, что, когда изменил» по финансам нет (LOW).
- Возвраты денег как отдельная операция в интерфейсе отсутствуют (есть только корректировка директором).

Операции, меняющие баланс, на рабочей базе не запускались. Все записи выполнялись только во временной тестовой БД.

## 9. Backup и disaster recovery

| Вопрос | Ответ [проверено] |
|---|---|
| Автоматические копии в работающем стенде | **Нет.** В dev-стеке сервиса нет, папки `backups/` не существует |
| Копии в prod-compose | Есть сервис `backup`: `pg_dump | gzip` каждые 24 ч, хранение 14 дней, в `./backups` на том же сервере |
| Вне сервера | **Нет** (только рекомендация в README) |
| Шифрование/права | Нет шифрования; доступ по правам файловой системы хоста |
| Проверено восстановление | **Нет** (BLOCKED без отдельной машины/окружения; процедура описана в README, не выполнялась) |
| Риск потерять БД при поломке сервера | **Да**, если копии лежат на том же диске |

**BKP-01 (HIGH).** До запуска нужна реально работающая и проверенная восстановлением схема.

**Рекомендуемая стратегия для учебного центра:**
- RPO ≤ 24 ч (ночной `pg_dump`); при желании ≤ 1 ч добавить WAL-архивацию или частые дампы (база ~150 МБ — дамп занимает секунды).
- RTO ≤ 2–4 ч: свежий VPS + `docker compose up` + восстановление дампа + заранее записанная инструкция.
- Копии: ежедневно локально 14 дней + ежедневно во внешнее хранилище (S3-совместимое или второй сервер), шифрование (`age`/`gpg`), еженедельная автоматическая проверка восстановления в изолированной БД с контрольным запросом (число учеников, сумма книги проводок).
- Проверку восстановления нужно выполнить один раз вручную до запуска и записать результат.
